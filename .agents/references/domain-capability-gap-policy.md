# Domain Capability Gap Policy

GDKP is domain-neutral. Unfamiliar subject matter alone is not a reason to download another Skill.

## Valid Gap

A DomainCapabilityGap exists only when a confirmed goal or acceptance test requires a specialized method, standard interpretation, validation protocol, file format, regulated procedure, or tool behavior that the active core and project Skills cannot perform reliably.

The internal gap record identifies:

- the affected goal, requirement, task, or acceptance test;
- the missing capability in operational terms;
- capabilities already checked;
- the practical consequence of using the generic fallback;
- required inputs, outputs, permissions, and validation method;
- whether the gap is optional or blocks safe completion.

Do not open Q5 for a broad field label, a desire for a stronger model, a task the core workflow can already perform, or a capability whose result would not affect the outcome.

## Existing Capability First

Before GitHub discovery, inspect active project Skills and verified built-in capabilities. Reuse a matching capability when its provenance, version, scope, permissions, and interface are compatible. Never activate a quarantined or drifted Skill.

## Discovery Boundary

`domain-skill-acquisition` alone may turn a verified gap into GitHub candidate discovery. Other Skills report the gap and continue safe independent work. A domain Skill is an execution dependency; it cannot become factual evidence, approve sources, publish canonical Notion content, control the graph, or take over orchestration.

## Fallback

If no eligible Skill exists or the user declines Q5, use the generic method and state its concrete limitation. Mark the project blocked only when a mandatory acceptance condition cannot be met safely without the missing capability.
